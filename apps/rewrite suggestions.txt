Here's the stack I'd actually bet on, split by layer — plus an honest note on where the Rust agent ecosystem is still thin.

Core (boring on purpose)
Tokio + axum + tower-http + sqlx + tracing/OpenTelemetry is the consensus default for a fresh Rust service, and it should stay the stable half of your stack through 2030.

Two sqlx 0.9 gotchas worth knowing before they bite: query functions now require impl SqlSafeStr (runtime-built strings must be wrapped in AssertSqlSafe), and Transaction/PoolConnection no longer implement Executor directly — pass &mut *tx. Actix-web is still faster on paper; axum wins on team throughput and Tower composability.

LLM layer
rig-core is effectively the only serious option. It ships 20+ providers, 10+ vector stores, full OpenTelemetry GenAI semantic conventions, MCP support, WASM compatibility, and real production users (Neon, Nethermind, Dria) — currently on the v0.39 line. Write against its CompletionModel trait so swapping a hosted provider for a self-hosted vLLM/Ollama endpoint is a constructor change, not a refactor.

Orchestration
Tokio's JoinSet + CancellationToken is the canonical pattern for sub-agent lifecycle management, and honestly it's enough for most systems. If you want a framework: AutoAgents (Ractor actor model) is the most complete Rust multi-agent framework, with ADK-Rust and OpenFANG as alternatives. Protocol layer — this is the real 2030 bet
MCP is where I'd invest architecturally. Ship every capability as an MCP server, and your backend stops being "an API with AI features" and becomes a tool surface any agent can drive. The official rmcp SDK is on 3.x, implementing the stable 2026-07-28 spec while staying compatible with 2025-11-25 and earlier. Two things matter in that revision: servers are stateless by default (no session ID, no standalone GET/DELETE stream), and standardized Streamable HTTP headers (Mcp-Method, Mcp-Name, Mcp-Param-*) let proxies and gateways route MCP traffic without parsing the JSON body — meaning you can do auth, rate limiting, and routing at the edge. Derive schemars::JsonSchema on your param structs and the tool schemas generate themselves. 
GitHub + 2

The upgrade story is reassuringly dull: one team's move from rmcp 0.14 to 3.1 cost two lines of Rust and a config file — the protocol boundary held.

Sandboxing
WASM sandboxing for tool isolation is one of the validated architectural patterns in this ecosystem. Wasmtime + the component model for anything agent-generated; gVisor/Firecracker only when you need a real filesystem and process tree.

Durability — the actual gap
Be clear-eyed here: checkpointing, crash recovery, and state reconstruction across failures are still on you — RIG does LLM calls, Swarms-rs and ADK handle orchestration, but durable execution is not yet a framework feature in Rust. Options: Temporal's Rust SDK is in public preview as of Replay 2026, or Restate, which ships a single-binary server, journals invocations, and supports Rust workflows as plain functions. The non-negotiable rule either way: LLM calls are non-deterministic and must be wrapped as journaled activity steps. If you want zero new infrastructure, a Postgres-backed journal (DBOS-style) is a legitimate third path. 
Wrenlearnsrust + 3

What I'd skip
Vector databases as separate infrastructure. pgvector inside the Postgres you already run covers 90% of university-scale RAG, and you keep transactions, backups, and RBAC in one place. Add LanceDB/Qdrant only when you've measured a reason.

The honest framing: the durable/agentic layer is where the ecosystem is genuinely immature, so keep it swappable behind your own traits — that's the difference between a 2030 stack and a 2027 rewrite.

Where this will actually hurt
Alembic autogenerate is gone. sqlx migrations are hand-written SQL with no model diffing. For a schema still in flux this is a real productivity tax. If it bites, SeaORM has a migration DSL — but you lose query! compile-time verification, which is the main reason to pick sqlx at all.

sqlx::query! needs a live database at compile time. Run cargo sqlx prepare and commit .sqlx/ or your CI breaks.

fastapi-users is ~2 weeks of work to replace. Registration, verification, password reset, OAuth flows. Serious alternative: don't rewrite it — put Keycloak or Zitadel in front and have axum validate JWTs via jwt-authorizer. For a university with existing identity infrastructure this is probably the right call regardless.

Judge0: keep it. Rewriting sandboxed multi-language code execution is not a dependency swap, it's a product. Wrap it in a typed reqwest client. Revisit wasmtime only if you narrow to WASM-compilable languages later.

Your ruff ignore list tells a story. Half of it is SQLModel's dual-typing confusing the type checkers. That entire category of pain disappears — but it's replaced by lifetime and Arc<AppState> friction that no Python experience prepares a team for. Budget for that.

Four things I got wrong last message, corrected from crates.io today: tower-http is 0.7.0 (not 0.6), reqwest is 0.13.4 (not 0.12), axum-extra is 0.12.6, and figment 0.10.19 has no toml feature — env-only config.

The one that matters most: apalis-postgres still depends on sqlx ^0.8.1 while your data layer would be on sqlx 0.9. That means two incompatible PgPool types in one binary, so no transactional enqueue — the entire reason to use a Postgres queue. The script routes around it with apalis-redis (which shares redis 1.x with your own code, so no duplicate versions). SETUP.md lists the three alternatives if you'd rather keep transactional enqueue and pin sqlx 0.8.6.

Also worth knowing: apalis 1.0.0-rc.9 is the real bleeding edge line (0.7.4 is max stable), and redis-rs reached 1.0 — which weakens my earlier fred recommendation, since redis-rs now has a stable API and apalis-redis already pulls it in.

Your MSRV floor is 1.94, set by sqlx 0.9 and jiff-sqlx.

The section I'd actually push you to read is "Staying bleeding edge without losing months." The technique that makes this affordable is architectural, not procedural: rig_core:: types appear in exactly one crate, sqlx:: in exactly one, apalis:: in exactly one. rig moved 0.39 → 0.41 in the two months since those releases, and it'll keep moving through your whole rewrite. With the firewall, that's a one-file diff; without it, it's a three-day refactor every quarter.
