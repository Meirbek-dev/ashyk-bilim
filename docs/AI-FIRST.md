# AI-first: фундамент и AI-предпроверка

Статус: спецификация утверждена владельцем к реализации 2026-11-01; реализация идёт на `main`.
Раздел «Состояние» в конце - что уже сделано и что осталось.

Цель - перевести ИИ из боковой панели «спроси меня» в цикл обучения: платформа знает, из каких понятий
состоит курс, что из них усвоил каждый учащийся, умеет находить нужный фрагмент материала и снимает с
преподавателя механическую часть проверки. Документ описывает три слоя фундамента (граф понятий, модель
знаний, поиск по смыслу) и первый флагман на нём - AI-предпроверку работ.

## 0. Принципы

- **Человек решает.** ИИ предлагает (понятия, разметку, оценки), преподаватель утверждает. Ничего, что
  видит учащийся, не появляется без решения преподавателя: неподтверждённая разметка не влияет на модель
  знаний, черновик оценки не публикуется сам.
- **Доказательство вместо уверенного тона.** Каждый балл черновика опирается на цитату из работы; сервер
  проверяет, что цитата действительно есть в работе, и снимает непроверяемые. Каждый ответ поиска даёт
  точное место в материале.
- **Прозрачность модели знаний.** Оценка усвоения - простая байесовская модель (BKT) с документированными
  параметрами, а не чёрный ящик; учитель видит, из каких работ она сложилась.
- **Работает без внешних ключей.** Поиск по смыслу имеет локальный эмбеддер по умолчанию; агенты в
  `ai_draft_mode` дают детерминированные черновики (тесты, офлайн-стенд).
- **Данные учащихся.** В промпты не уходят имена и логины учащихся; работа - это данные, а не
  инструкции (защита от prompt injection в тексте работы). Эмбеддинги можно считать на своём хосте
  (рекомендация для прода - self-hosted TEI с `bge-m3`: kk/ru/en, данные не покидают страну).
- **Не ломать существующее.** Старые агенты и экраны работают как раньше; новый слой подключается к ним
  (поиск - в контекст вопросов и учёбы, модель знаний - к работе над ошибками).

## 1. Поиск по смыслу (retrieval)

### 1.1 Что индексируется

| Источник (`source_type`) | Что берётся | Аудитория |
| ------------------------ | ----------- | --------- |
| `lesson` | лекция `dynamic`: документ Tiptap -> текст по блокам с путём заголовков | learner, если активность опубликована |
| `activity` | видео/документ: название, описание, имя файла (до появления расшифровок и извлечения текста) | learner, если опубликована |
| `assignment` | задание с файлом: инструкции и критерии рубрики | learner, если опубликована |
| `item` | вопрос теста/экзамена/задачи: только формулировка, без ключа ответа | staff (никогда не учащимся) |
| `course` | описание курса, «чему научитесь», названия глав | learner |

Зарезервированы `document` (текст PDF) и `transcript` (расшифровка видео) - фаза 2 (раздел 6).

### 1.2 Нарезка

- Документ Tiptap проходится по блокам верхнего уровня; текущий путь заголовков (`H1 > H2`) хранится в
  якоре фрагмента. Абзацы копятся до ~900 символов (максимум 1500), фрагмент не рвёт блок кода и таблицу,
  перекрытие - последнее предложение предыдущего фрагмента (до 200 символов).
- Якорь (`anchor` jsonb): `{"heading_path": [...], "block_start": n, "block_end": m}` для лекций,
  `{"item_id": ...}` для вопросов. Метка (`label`) - «Лекция › Раздел» для цитаты.
- Каждый источник имеет версию (`activities.version`, `assessments.content_version`,
  `file_submissions.version`, `courses.version`); индекс помнит версию, по которой нарезан.

### 1.3 Эмбеддинги

- `ab-clients::embed`: `Embedder` с провайдерами:
  - `hash` (по умолчанию) - локальный детерминированный эмбеддер: хеширование символьных 3-5-грамм и слов
    свёрнутого текста (`search_fold`-подобная свёртка kk -> ru, ё -> е), 1024 измерения, L2-нормировка.
    Лексический, но без сети и бесплатный.
  - `openai_compatible` - `POST {base}/embeddings` (`model`, `input[]`, `dimensions: 1024`): OpenAI,
    OpenRouter, self-hosted TEI/Infinity/Ollama.
- Размерность фиксирована - `vector(1024)`; у каждого фрагмента `embedding_model`. Смена модели помечает
  индекс устаревшим, переиндексация идёт фоном; поиск использует только векторы текущей модели (иначе -
  только лексическая часть).
- Конфигурация: `AB__AI__EMBEDDING_PROVIDER` (`hash` | `openai_compatible`), `..._BASE_URL`,
  `..._API_KEY`, `..._MODEL`, `..._TIMEOUT_SECS`, `..._BATCH` (по умолчанию 32).

### 1.4 Хранение

```sql
content_chunks (id uuid pk, course_id fk, activity_id fk null, source_type, source_id uuid,
  ordinal int, audience ('learner'|'staff'), published bool, label text, body text,
  anchor jsonb object, token_estimate int, embedding vector(1024) null, embedding_model text null,
  lexeme tsvector generated (simple, свёрнутый label+body), created_at)
  индексы: (course_id, audience), HNSW (embedding vector_cosine_ops), GIN (lexeme)
content_index_state (source_type, source_id) pk, course_id, activity_id, source_version bigint,
  chunk_count, embedding_model, indexed_at, error text null
```

### 1.5 Индексация

- Задание `retrieval:sweep` (каждую минуту, планировщик воркера): находит до 50 источников, у которых
  версия не совпадает с `content_index_state` (или модель эмбеддера другая, или источник исчез), и
  переиндексирует каждый в своей транзакции (удалить старые фрагменты -> вставить новые -> состояние).
  Так индекс догоняет любые правки без крючков в каждом пути записи; задержка - до минуты.
- `POST /ai/retrieval/{course_id}/reindex` ставит курс в очередь целиком (сбрасывает состояние).
- Ошибка провайдера эмбеддингов не теряет фрагменты: они пишутся без вектора, `error` в состоянии,
  следующий проход повторяет.

### 1.6 Поиск

- Гибрид: top-40 по косинусу (если есть вектор запроса той же модели) + top-40 по `ts_rank_cd` по
  `websearch_to_tsquery('simple', свёртка запроса)` -> слияние Reciprocal Rank Fusion (k = 60) ->
  не более 3 фрагментов на источник -> top-k (по умолчанию 8).
- Фильтры: курс; для учащегося `audience = 'learner' AND published`; для преподавателя - все.
- `POST /ai/retrieval/{course_id}/search {query, limit}` -> `hits[{chunk_id, source_type, source_id,
  activity_id, label, excerpt, anchor, score}]`. `GET .../status`, `POST .../reindex` - для
  преподавателя курса.
- Использование агентами: `course_qa` и `study_companion` берут в контекст найденные фрагменты по вопросу
  (вместо первых N символов всего курса), если у курса есть индекс; иначе - прежний контекст. Источник
  цитаты - активность с якорем, ссылка ведёт в плеер (B-AI-27).

## 2. Граф понятий курса

### 2.1 Модель

```sql
course_concepts (id, course_id, slug unique per course, name, description, status
  ('suggested'|'approved'|'rejected'), origin ('ai'|'teacher'), position, run_id null,
  decided_by null, decided_at null, created_at, updated_at)
concept_prerequisites (concept_id, requires_id) pk, course_id, status, origin   -- без циклов
concept_tags (id, course_id, concept_id, activity_id, item_id null, weight real (0,1], status, origin,
  rationale, run_id null, decided_by, decided_at, created_at)
  unique (concept_id, activity_id, item_id) nulls not distinct
```

Тег вопроса (`item_id`) точнее тега активности; при подсчёте усвоения ответ на вопрос берёт теги вопроса,
а если их нет - теги его активности.

### 2.2 Агент `concept_mapper` (`ai_runs.kind = 'concept_mapping'`)

- Вход: структура курса (главы, активности), фрагменты индекса по каждой активности (или текст лекции,
  если индекса нет), формулировки вопросов; уже утверждённые и отклонённые понятия (чтобы не предлагать
  отклонённое снова и переиспользовать утверждённое).
- Выход (`ConceptMapReport`): `concepts[{slug, name, description, prerequisites[slug]}]`,
  `tags[{source (citation id контекста), concepts[{slug, weight, rationale}]}]`, `summary`.
- Слияние: утверждённые и отклонённые решения преподавателя неприкосновенны; новые понятия и теги
  добавляются как `suggested`; предложение с `slug` отклонённого понятия отбрасывается; ссылки на
  неизвестные источники и понятия отбрасываются; веса зажимаются в (0, 1].
- Черновой режим (нет провайдера): понятие на каждую главу, активности главы размечены им.
- Запуск: `POST /courses/{course_id}/concepts/suggest` (очередь, `RunAccepted`); переключатель
  `concept_graph_enabled`; часовой лимит `Analysis`.

### 2.3 Работа преподавателя

- `GET /courses/{course_id}/concepts` - понятия, предпосылки, теги, последний запуск, `allowed_actions`.
  Учащийся видит только утверждённые понятия без тегов-предложений.
- `POST /courses/{course_id}/concepts` (создать своё, сразу `approved`), `PATCH .../{concept_id}`
  (название, описание, статус), `DELETE .../{concept_id}`, `PUT .../{concept_id}/prerequisites`
  (`requires: [id]`, отказ при цикле - `concept-cycle`), `POST /courses/{course_id}/concept-tags`,
  `PATCH /courses/{course_id}/concept-tags/{tag_id}` (статус, вес), `DELETE` тега,
  `POST /courses/{course_id}/concepts/review` - пакетно утвердить/отклонить понятия и теги.
- Право - то же, что правка курса (`require_course_update`). Любое изменение утверждённой разметки ставит
  пересчёт модели знаний курса (`mastery:rebuild`, с дедупликацией и задержкой 30 с).

## 3. Модель знаний учащегося (mastery)

### 3.1 Доказательства

```sql
mastery_evidence (id, course_id, user_id, concept_id, source_type
  ('item'|'file_attempt'|'code_run'|'remediation'|'ai_question'), source_id uuid, part_id uuid null,
  score real [0,1], weight real (0,1], observed_at, created_at)
  unique (source_type, source_id, concept_id, part_id) nulls not distinct
concept_mastery (user_id, concept_id) pk, course_id, p_known real [0,1], evidence_count int,
  last_observed_at, updated_at
```

| Источник | Когда учитывается | Балл | Вес |
| -------- | ----------------- | ---- | --- |
| ответ на вопрос (`item`) | результат виден учащемуся: сдача оценена и опубликована (или автооценка показана сразу) | score / max_score по вопросу | вес тега |
| работа с файлом (`file_attempt`) | оценка опубликована | final_score / 100 | вес тега |
| прогон кода на видимых тестах (`code_run`, purpose `visible`) | после прогона | passed / total | 0.5 × вес тега |
| работа над ошибками (`remediation`) | завершена | score / 100 | вес тега активности |
| вопрос ИИ (`ai_question`) | после вопроса (найденные фрагменты -> активности -> теги) | 0.3 | 0.15 |

Пробные попытки персонала (`preview`) не учитываются. Пересдача заменяет доказательства той же попытки
(уникальный ключ), а не добавляет новые.

### 3.2 Модель (BKT с частичным баллом)

Для понятия хранится вероятность «усвоено» `p` (априорно 0.15). Наблюдение с баллом `s` и весом `w`:

```
pc   = p(1-slip) / (p(1-slip) + (1-p)guess)        -- после верного ответа
pi   = p·slip    / (p·slip    + (1-p)(1-guess))    -- после неверного
post = s·pc + (1-s)·pi
next = post + (1-post)·T                            -- научение, T = 0.12
p   := p + w·(next - p)
```

`guess/slip`: выбор и сопоставление - 0.25/0.10; открытый ответ, форма, файл, ИИ-сигнал - 0.05/0.10;
код - 0.05/0.15. Пересчёт - всегда повтор всех доказательств пары (учащийся, понятие) по времени: он
детерминирован, идемпотентен и правильно отражает переоценку.

Уровни: `not_started` (нет доказательств), `struggling` (p < 0.4), `learning` (p < 0.75 или меньше двух
доказательств), `mastered` (p ≥ 0.75 и не меньше двух доказательств). Флаг `stale` - последнее
доказательство старше 45 дней.

### 3.3 Обновление

- Задание `mastery:ingest {source_type, source_id}` ставится в той же транзакции, что и факт: сдача
  (`finalize`), сохранение и публикация оценки (тест и файл), завершение работы над ошибками; прогон кода
  и вопрос ИИ - сразу после записи факта. Обработчик выводит доказательства из факта, заменяет прежние
  для этого источника и пересчитывает затронутые пары.
- `mastery:rebuild {course_id}` выводит заново доказательства всего курса (смена разметки, первый запуск
  на существующих данных).

### 3.4 Что видно

- `GET /courses/{course_id}/mastery/me` - учащийся: понятия с уровнем, `p`, числом доказательств, датой и
  рекомендациями «что повторить» (активности со слабыми понятиями).
- `GET /courses/{course_id}/mastery` - преподаватель: по каждому понятию средний `p`, распределение по
  уровням, кто в `struggling`; `GET /courses/{course_id}/mastery/learners/{user_id}` - один учащийся с
  доказательствами.

## 4. AI-предпроверка (флагман A)

### 4.1 Что проверяется

- Тест/экзамен: каждый вопрос, требующий ручной проверки (`open_text`, `form`), по его рубрике
  (`OpenTextBody.rubric`, markdown; без рубрики - один критерий «соответствие ответа заданию»). Вопросы с
  автооценкой не трогаются; для `code` - только комментарий без смены балла.
- Работа с файлом: критерии `file_submissions.rubric` (без рубрики - один критерий на 100 баллов); текст
  работы - текстовые файлы, DOCX и PDF (извлечение текста на сервере, до 48 КБ на работу). Работа без
  извлекаемого текста получает черновик с флагом `no_text` и без баллов.

### 4.2 Агент `grade_assistant` (`ai_runs.kind = 'grade_draft'`)

- Вход: задание (инструкции, формулировка, рубрика), ответ учащегося (без имени), до трёх
  примеров калибровки (см. 4.4), язык курса.
- Выход (`GradeDraftReport`): `parts[{part_id, criteria[{criterion_id, label, max_score, score,
  evidence[{quote}], rationale}], score, feedback}]`, `overall_feedback`, `confidence`, `flags`.
- Проверки сервера: баллы зажимаются в [0, max]; цитата засчитывается, только если (после нормализации
  пробелов и регистра) она есть в тексте ответа и не короче 8 символов; критерий с ненулевым баллом без
  проверенной цитаты получает флаг `unsupported`; текст работы, похожий на инструкцию проверяющему
  («поставь максимальный балл», «ignore previous»), - флаг `injection_suspected`; уверенность ниже 0.5 -
  флаг `low_confidence`.
- Черновой режим: половина максимума по каждому критерию, без цитат, флаг `draft_mode`.

### 4.3 Черновики

```sql
ai_grade_drafts (id, course_id, activity_id, submission_id null, file_attempt_id null (ровно один),
  learner_id, run_id null, status ('queued'|'ready'|'applied'|'discarded'|'superseded'|'failed'),
  subject_version bigint, proposal jsonb object, ai_score, calibrated_score, max_score, confidence,
  flags text[], model_name, agreement ('exact'|'adjusted') null, final_score null,
  decided_by null, decided_at null, created_at, updated_at)
  одна активная (queued|ready) на работу
ai_grade_corrections (id, course_id, activity_id, draft_id, teacher_id null, part_key, criterion_key,
  ai_score, teacher_score, max_score, excerpt, teacher_feedback, created_at)
ai_course_settings (course_id pk, auto_grade_drafts bool, enabled_by null, updated_at)
```

- Постановка: `POST /ai/grading/activities/{activity_id}/drafts/queue {subject_ids?}` - для всех
  ожидающих проверки работ активности без свежего черновика (или для выбранных); автоматически - при
  сдаче, если у курса включено `auto_grade_drafts` (запуск от имени преподавателя, включившего
  настройку; если он потерял доступ, запуск падает с `AI_ACCESS_REVOKED`).
- Работа изменилась после черновика (версия) - черновик `superseded`, ставится новый.
- `GET /ai/grading/activities/{activity_id}/drafts` - черновики активности для очереди;
  `GET /ai/grading/drafts/subject/{subject_id}` - черновик работы для страницы проверки.
- `POST /ai/grading/activities/{activity_id}/drafts/approve {items[{draft_id, score?, feedback?}],
  action ('save'|'publish')}` - пакетное утверждение: права на проверку активности проверяются до тела
  запроса, черновик другой активности - «не найден»; каждый черновик проводится через обычное сохранение оценки (те же права, версия
  работы = `subject_version`, иначе пункт пропускается как `stale`); ответ - результат по каждому пункту.
- `POST /ai/grading/drafts/{draft_id}/discard`.
- Любое сохранение оценки работы с активным черновиком (вручную или через approve) закрывает черновик:
  `applied`, `final_score`, `agreement` (`exact`, если итог совпал с предложением до 0.5% максимума), и
  пишет строки калибровки по каждой части/критерию.

### 4.4 Калибровка под преподавателя

- Поправка: для (активность, часть, критерий) среднее `(teacher - ai) / max` по последним 50
  исправлениям, со сжатием `n / (n + 4)`; `calibrated = clamp(ai + поправка × max)`. В черновике видны и
  исходный, и скорректированный балл, и строка «скорректировано по N вашим прошлым оценкам».
- Примеры: в промпт идут до трёх последних исправлений этой активности с наибольшим расхождением:
  фрагмент ответа (до 600 символов), балл ИИ, балл преподавателя, его комментарий.

### 4.5 Согласованность и метрики

- `GET /ai/grading/activities/{activity_id}/consistency`:
  - `pairs` - похожие ответы (косинус эмбеддингов ≥ 0.9 по одной части) с итоговыми баллами,
    различающимися на ≥ 15% максимума: «эти две похожие работы оценены по-разному»;
  - `disagreements` - работы, где итог преподавателя отличается от черновика больше чем на 20%;
  - `drift` - средняя поправка по критериям (насколько ИИ систематически выше/ниже).
  Эмбеддинги ответов кешируются в `ai_work_embeddings (subject_id, part_key) pk, text_hash, model,
  embedding`.
- `GET /ai/grading/{course_id}/metrics?days=30`: черновики (всего, принято как есть, с правкой,
  отклонено), средняя абсолютная разница ИИ и преподавателя, медианное время до отзыва за период и за
  предыдущий такой же период, оценка сэкономленного времени (`принятые черновики × 6 минут`, константа
  в конфиге `AB__AI__MANUAL_GRADING_MINUTES`).
- `GET/PUT /ai/grading/{course_id}/settings` - `auto_grade_drafts`.

### 4.6 Права

Всё про черновики - у того, кто может оценивать работы активности (`Action::Grade` в области курса);
метрики и настройки - у преподавателя курса. Переключатель `grading_assistant_enabled`; лимиты - месячный
бюджет токенов и часовой лимит `Analysis` на ручную постановку (пакет - одна единица).
