# Модернизация, этап 2: ТЗ и техническая архитектура `apps/web`

Статус: черновик на утверждение владельцем. Дата: 2026-10-02.
Область: перепись `apps/web` с нуля на React 19 + TanStack Start (и семейство TanStack) + Paraglide JS,
с переосмыслением архитектуры. Плюс изменения в `apps/server`, CI и compose, без которых
новая архитектура невозможна (раздел 9).
Основание: `docs/MODERNIZATION-STAGE-1.md`, раздел 6 (контракт веба), `docs/GATES-BASELINE.md`,
аудит `apps/web` на `main` = 40e0512.

Разработка ведётся агентами (Fable 5.1, Opus 5.5, GPT-6 Astra и др.) с минимальным человеческим ревью.
Поэтому главное требование документа: **каждое архитектурное правило проверяется машиной**.
Правило, которое нельзя проверить гейтом, считается пожеланием и в документ не включается.

---

## 1. Цель

Текущий `apps/web` - форк LearnHouse на Next.js, переживший смену бэкенда, три поколения подходов
к данным и сотни точечных правок gauntlet-цикла. Он работает, но в нём на каждую задачу есть
два-пять способов её решить, и следующий агент выбирает случайный. Этап 2 заменяет его приложением, где:

1. На каждую задачу есть **ровно один** способ, и отклонение от него не проходит CI.
2. Веб - слой отображения. Он не хранит секретов, не проксирует API и не ставит cookie.
3. Типы, ключи запросов, маршруты и тексты выводятся из источников правды (OpenAPI, дерево файлов,
   каталоги сообщений) и проверяются компилятором, а не скриптами-латками.
4. Один образ работает на любом домене (контракт этапа 1), а e2e в CI гоняется по собранному образу.
5. Функциональность для пользователя сохранена полностью; покрытие 230 операций API контролирует гейт,
   а не память исполнителя.
6. Несколько агентов могут работать параллельно, не пересекаясь по файлам.

Новая перепись будет находиться в apps/web-2 

## 2. Границы

**В области:** весь `apps/web`; `apps/server` в объёме раздела 9.1; `compose.prod.yaml` (блок `web`),
`compose.smoke.yaml`, `.github/workflows/ci.yaml` (web-гейты, e2e-джоб), корневой `package.json`,
`justfile` (web-рецепты), `docs/` (веб-документы), `apps/web/AGENTS.md`, редизайн, сделать пользовательский интерфейс и опыт более продуманным и консистентым.

**Жёсткие ограничения:**

- Данные, уже лежащие в БД, должны читаться новым вебом без миграции: документы Tiptap
  (включая обе формы embed-узлов), markdown-контент, конфигурации заданий, секции профиля, имя темы.

**Предпосылки.** Этап 1 в работе: коммит 40e0512 в `main`, CI по нему красный (web lint, shellcheck),
`docs/INFRA.md` ещё не написан. Разработку этапа 2 это не блокирует; cutover (Ф8) требует завершённого
Э3 этапа 1 (образы из GHCR, `just deploy` / `rollback`).

## 4. Принципы

1. **Веб не BFF.** Браузер ходит в `/api/v2` сам (same-origin). Сервер веба рендерит документ и больше ничего.
2. **Один способ на задачу.** Таблица 6.2 перечисляет задачи и единственный разрешённый механизм; остальное запрещено линтом.
3. **Источник правды один, остальное выводится.** Типы и ключи - из OpenAPI, ссылки - из дерева маршрутов,
   тексты - из каталогов. Сгенерированное не коммитится и не правится.
4. **Wire-формы без адаптеров.** Компоненты работают с типами контракта как есть.
5. **Состояние живёт там, где ему место.** Серверное - в Query, навигационное - в URL, остальное - локально.
6. **Модуль фичи замкнут.** Свои файлы, свои сообщения, публичный вход один.
7. **Нет уровня "предупреждение".** Правило либо ошибка, либо выключено. Нулевой допуск с первого коммита.
8. **Переносится поведение, а не код.** Старый код - справочник. Список исключений - в 10.3.

## 5. Требования

### 5.1 Функциональные

- **R-01 Паритет функций.** Весь объём раздела 8 доступен пользователю. Машинный критерий: каждая операция
  OpenAPI либо вызывается новым вебом, либо внесена в список неиспользуемых с причиной (гейт G-10).
- **R-02 Паритет данных.** Любой документ редактора и любой markdown из прод-БД отображается без потерь
  (корпусный тест на восстановленных прод-данных, G-12).
- **R-04 Три локали** (ru - базовая, kk, en) с полным паритетом ключей, аргументов и форм множественного числа.
- **R-05 Один образ на любой домен.** Конфигурация только во время выполнения: `PUBLIC_ORIGIN`, `INTERNAL_API_URL`.
- **R-06 Сессия - только cookie сервера.** Веб не читает содержимое `ab_session`, не ставит и не удаляет её.
- **R-07 Доступ описан один раз** (6.4) и используется и guard'ами, и навигацией.
- **R-08 Состояние экрана передаётся ссылкой:** фильтры, вкладки, сортировка, выбранный элемент, тред AI - в search-параметрах.
- **R-09 Попытка экзамена не теряет ответы** при перезагрузке, обрыве сети и конфликте версий; механизм черновика один (6.6).
- **R-10 CSP с nonce** на каждом документе (6.10).
- **R-11 Доступность:** ни одного нарушения уровня serious/critical по axe на маршрутах, покрытых e2e;
  все интерактивные элементы - из UI-кита.

### 6.3 Рендеринг и серверный слой

**Сервер веба делает ровно пять вещей:** рендерит документ; отдаёт статику; отвечает на `GET /healthz`;
принимает `POST /_client-error` (отчёт об ошибке браузера -> JSON в stdout, лимит размера и частоты);
выполняет middleware запроса (локаль, nonce, `x-request-id`, легаси-редиректы).

Запрещено: `createServerFn` и серверные маршруты, обращающиеся к API ради данных; запись cookie;
любые запросы к API, кроме GET во время SSR (клиент API на сервере бросает исключение на не-GET).
Это снимает W-01, W-02, W-05 и переменную `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`.

**Клиент API изоморфен** (`createIsomorphicFn`):

| Среда   | База                | Заголовки                                                                                         |
| ------- | ------------------- | ------------------------------------------------------------------------------------------------- |
| Браузер | `/api/v2`           | cookie уходит сама (same-origin)                                                                  |
| SSR     | `INTERNAL_API_URL`  | пробрасываются `cookie` (только `ab_session`), `accept-language`, `user-agent`, `x-forwarded-for`, `x-request-id`, `traceparent` |

`Set-Cookie` при SSR не пробрасывается: продление сессии происходит на прямых запросах браузера.
Повторы - в одном месте: Query повторяет GET один раз при сетевой ошибке или 5xx; 4xx не повторяются.

**Режим SSR по группам маршрутов** (опция `ssr` маршрута; потомок может только ужесточить):

| Группа                                        | `ssr`         | Почему                                                                                   |
| --------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------- |
| Публичные: лендинг, каталог, курс, сертификат, профиль, вход | `true` | первая отрисовка, OG-теги, ссылки в мессенджерах                                    |
| Рабочие области: плеер, попытка, студия, админка, аналитика  | `'data-only'` | loader выполняется на сервере (данные приходят в документе), компонент рендерится в браузере: расхождений гидрации нет по построению, редакторы и графики не тянутся в SSR |

Ответ документа: `Cache-Control: private, no-store`. Хешированные ассеты: `public, max-age=31536000, immutable`
(контракт этапа 1; edge кэширует только их). Обработчик `vite:preloadError` один раз перезагружает страницу,
если после деплоя запрошен чанк прошлой сборки.

**Часовой пояс.** Все даты показываются в поясе платформы (`Asia/Almaty`, одна константа в `format.ts`)
и на сервере, и в браузере. Сроки однозначны, вывод SSR и клиента совпадает, полифилы `Intl` не нужны.

### 6.5 Данные

**Контракт.** Генератор читает `apps/server/openapi.v2.json` **без трансформаций**. Дефекты контракта чинятся
в сервере (9.1). Результат (`shared/api/generated/`) не коммитится; `bun run codegen` запускается из
`postinstall` и перед `typecheck`, `lint`, `test`, `build`. Дрейфа между спецификацией и клиентом
не может быть по построению, гейт "diff сгенерированного" исчезает.

Генерируется: типы, zod-схемы, SDK-функции, фабрики `xOptions()` / `xInfiniteOptions()` / `xMutation()` /
`xQueryKey()`. Хуки не генерируются. Ответы проверяются zod-схемой в dev, тестах и e2e (расхождение
контракта роняет тест); в прод-сборке проверка отключена и схемы ответов вырезаются из бандла.

**Правила использования:**

- Типы контракта используются как есть. `*_uuid`, префиксы `course_` / `activity_`, глобальные ambient-типы,
  индексные сигнатуры `[key: string]: unknown` запрещены (G-02; `git grep course_uuid` пуст).
- `features/<x>/api.ts` содержит только композицию: `select`, объединение опций, оптимистичные обновления,
  карту "мутация -> инвалидируемые ключи". Сырых HTTP-вызовов в фичах нет.
- Keyset-списки - `useInfiniteQuery` и "показать ещё" / бесконечная прокрутка. Номера страниц поверх
  курсоров не эмулируются. Списки с `page` / `page_size` по контракту (аналитика, очередь работ) остаются постраничными.
- Оптимистичные блокировки: `If-Match` из версии сущности, `ETag` из ответа кладётся обратно в кэш.
  Конфликт (409 / 412) обрабатывается одним компонентом диалога. Сохранение курса обязано слать `If-Match`
  (сейчас не шлёт, W-21); если контракт курса версии не даёт - это пункт 9.1.
- Идемпотентность: ключ создаётся в момент начала логического действия и переживает повторы.
- `defaultPreloadStaleTime: 0` у роутера: свежестью управляет только Query. `staleTime` по умолчанию 30 с;
  отклонения задаются в `api.ts` фичи с комментарием.

**SSE.** Одна обёртка `subscribe(path, { onEvent, signal })` с `Last-Event-ID`, повторным подключением и
обработкой 401. Потребители: события проверки курса (инвалидация ключей оценивания), события одной сдачи
(`GET /submissions/{id}/events` - сейчас вебом не используется, заменяет опрос), AG-UI (`HttpAgent` поверх
того же fetch). Опрос структуры курса раз в 30 с удаляется.

| Глобальное клиентское                 | TanStack Store, только: состояние сессии редактора блоков (панели, выделение), очередь несохранённых ответов попытки |

**Формы.** Схема - сгенерированная zod-схема тела запроса; UI-специфика добавляется через `.extend()` в фиче.

очищается. Один хук `useAttemptDraft`. Конфликт версий разрешается одним диалогом. Поведение покрыто
unit-тестами модели (включая property-тесты очереди) и e2e: перезагрузка, офлайн, вторая вкладка.

### 6.7 i18n (Paraglide)

- **Локали:** `ru` (базовая), `kk`, `en`. Старые теги `ru-RU` / `kk-KZ` / `en-US` и префикс `/kz` остаются только
  в таблице редиректов.
- **Стратегия:** `['cookie', 'preferredLanguage', 'baseLocale']`, без локали в URL. Причины: контент курсов
  не переводится (переводится только оболочка), поэтому локализованные URL дают дубли, а не SEO; ссылка,
  отправленная преподавателем, открывается у студента на его языке; каждая ссылка в коде становится проще.
  Переключатель языка ставит cookie, сохраняет выбор в профиль (поле `locale` уже есть в контракте) и
  перезагружает страницу. При входе без cookie локаль берётся из профиля.
- **Сервер:** `paraglideMiddleware` в `server.ts`; `<html lang>` выставляется при SSR. Определение локали одно.
- **Каталоги:** `messages/<locale>/<feature>.json`, по файлу на фичу (снимает W-33). Ключи плоские,
  snake_case, с префиксом фичи (`grading_review_save`), валидные идентификаторы JS. Ключи отсортированы (fmt).
- **Динамических ключей нет.** Перечисление сервера отображается в текст через исчерпывающую карту:
  `const errorText = { ... } satisfies Record<ErrorCode, () => string>`. Новый код ошибки в контракте без
  перевода - ошибка компиляции; `sync-error-codes.mjs` не нужен. То же для статусов, типов активностей,
  кодов аналитики.
- **Множественное число** - варианты inlang (`plural`), для ru формы one/few/many/other, для kk и en - one/other.
  `select` - только по стабильному перечислению, никогда по переведённому слову.
- **Перенос текстов.** Каталоги не конвертируются целиком: ~24% ключей мертвы. Сообщение создаётся, когда
  новый код его использует; формулировка берётся из старого ru-каталога (он вычитан gauntlet-циклом).
  Глоссарные правила из тестов `i18n/*` (kk "Болдырмау", единицы размера) становятся проверками каталога.
- **Форматирование** - только `shared/i18n/format.ts`: дата, время, относительное время, число, процент,
  размер файла, длительность. Локаль из `getLocale()`, пояс платформы.

  одна обёртка таблицы (состояние - в search-параметрах), одно состояние загрузки (skeleton).
- Только токены темы. `docs/DESIGN_GUIDELINES.md` переписывается в проверяемые правила; гейт G-11 ищет
  классы палитры, произвольные цвета и inline-стили. Исключения - список файлов в конфиге гейта с причиной
  (например, цвета графиков).
- **Темы.** Тема = CSS-файл с переменными под `[data-theme=<name>]`, подгружается ссылкой; в JS-бандл темы
  не входят. Тёмный режим включается одним способом (атрибут на `<html>`, выставляется при SSR из cookie;
  режим "как в системе" - через `prefers-color-scheme` в CSS). Состав тем - вопрос Q2.
- **Ленивые границы** (G-08): редактор блоков, markdown-редактор, Monaco, shiki, katex, графики, видеоплеер,
  PDF, emoji-picker, тяжёлые embed-провайдеры. Иконки импортируются поимённо.
- **Редактор блоков.** Одно ядро Tiptap с пресетами (авторинг, просмотр, обсуждение) и markdown-редактор
  на том же ядре. Схема документа обязана читать все типы узлов из прод-данных (R-02). Новый редактор пишет
  embed только в одной форме (`embedBlock`), старую (`blockEmbed`) читает через отображение при загрузке.
  YouTube встраивается одним способом.
- React Compiler включён; ручные `useMemo` / `useCallback` не пишутся.

### 6.9 Ошибки, загрузка, наблюдаемость

- Иерархия: `errorComponent` и `notFoundComponent` у корня и у каждого макета-оболочки; `pendingComponent` -
  skeleton оболочки. Виджет внутри страницы оборачивается границей из кита, если его отказ не должен ронять страницу.
- Ошибка API - всегда `ApiError` (`code`, `fieldErrors`, `requestId`, `retryAfter`). Текст - из карты кодов (6.7).
  Тост показывает `presentError(error)`; ветвление в коде - только по `error.code`.
- Запрос с пустым результатом и запрос с ошибкой отображаются по-разному: `?? []` поверх ошибки запрещён
  (с `useSuspenseQuery` ошибка уходит в границу сама).
- Логи сервера веба - JSON в stdout с `request_id`. Ошибки браузера (`window.onerror`, границы ошибок) уходят
  в `POST /_client-error`. Внешних сервисов мониторинга нет (решение владельца на этапе 1).

### 6.10 Безопасность

- **CSP** ставит middleware на каждый документ: `script-src 'self' 'nonce-<n>' 'strict-dynamic'`;
  `style-src 'self' 'unsafe-inline'` (Monaco, Tiptap и графики вставляют стили); `connect-src 'self'`;
  `img-src 'self' data: blob: https:`; `frame-src https:` (embed-провайдеры); `worker-src 'self' blob:`;
  `object-src 'none'`; `base-uri 'self'`; `frame-ancestors 'none'`. В e2e политика уже принудительная:
  нарушение CSP в консоли роняет тест.
- Прокси аватаров Google удаляется: `<img referrerpolicy="no-referrer">` напрямую. Если воспроизведутся
  отказы Google - сервер копирует аватар в хранилище при входе (пункт 9.1, по необходимости).
- CSRF обеспечивает сервер (`SameSite=Lax` + проверка `Origin`); веб мутаций с сервера не делает.
- Секретов у веба нет. `env.server.ts` разбирает две переменные один раз при старте и падает при ошибке.
- Защита экзамена (blur, копирование, fullscreen) - клиентская мера из старого веба, переносится как есть;
  решения о нарушениях принимает сервер.

## 10. Процесс агентной разработки

### 10.1 Цикл

Как на переписи сервера: gauntlet-цикл по плану раздела 11. Оркестратор берёт следующую фазу, раздаёт срезы
субагентам (параллельно там, где план помечает `∥`), полный набор гейтов запускается **один раз на фазу**;
внутри фазы - `typecheck`, точечные тесты и e2e своей фичи. Статус срезов отмечается в таблицах раздела 11.

### 10.2 Срез фичи

1. **Сбор поведения.** Агент читает старый код фичи, её тесты (`BUG-` / `UX-` закрепления), записи `GAUNTLET.md`
   и операции контракта; результат - чек-лист поведения в описании среза. Чистая логика выделяется в `model/`.
2. **Реализация** по образцу эталонного среза (Ф1): маршруты, `api.ts`, компоненты, сообщения на трёх языках.
3. **Проверка:** unit-тесты модели, e2e-сценарии по чек-листу, проход в браузере на трёх локалях.
4. **Готово, когда:** гейты зелёные; операции фичи исчезли из `api-unused.json`; легаси-маршруты фичи
   редиректятся; в `src/` нет TODO и заглушек.

### 10.3 Правила

- **Что можно копировать из старого кода:** расширения Tiptap (они задают схему данных), чистые функции с
  тестами, тексты каталогов, справочники (embed-провайдеры, шаблоны формул). Всё остальное пишется заново.
- **Параллельность.** Срезы разных фич не пересекаются по файлам: свои каталоги, свои файлы сообщений,
  сгенерированное не в git. Изменения `shared/` и добавление примитивов кита - отдельными коммитами
  оркестратора, не субагентов.
- **Перекрёстное ревью вместо человеческого.** В конце фазы diff проверяет модель другого семейства, чем
  автор (например, код Fable/Opus проверяет GPT-6 Astra и наоборот) с заданием искать дефекты, а не
  подтверждать. Подтверждённые находки исправляются до закрытия фазы.
- **Новое правило = новый гейт.** Если ревью находит класс ошибок, в ту же фазу добавляется линт-правило или
  проверка, а не абзац в `AGENTS.md`.
- **Версии.** TanStack Start выходит несколько раз в неделю; обновление - отдельный коммит на границе фазы.
- Вопросы, которые может решить только владелец, - в `QUESTIONS.md`; работа не останавливается, действует
  значение по умолчанию.
