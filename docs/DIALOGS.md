# Диалоги: личные сообщения

Статус: техническое задание, утверждено 2026-11-10 (все решения раздела 14 приняты по умолчанию), этап 1 в
работе на ветке `wt/dialogs`.

«Диалоги» - переписка один на один между людьми платформы: учащийся пишет преподавателю своего курса,
преподаватель - учащемуся, члены команды курса - друг другу. Сегодня такого канала нет: вопрос «лично
преподавателю» уходит в мессенджеры вне платформы, а рекомендация аналитики «Написать личное сообщение»
(`send_personal_message`, `domain/src/analytics/risk.rs`) заканчивается отметкой `message_sent` в журнале
вмешательств без самого сообщения.

## 0. Принципы

- **Малая поставка.** На платформе около 175 активных учащихся, в обсуждениях курсов за всё время 2 записи
  (REWRITE 10). Этап 1 - текст один на один и ничего больше; вложения, рассылки и почта - отдельные этапы
  (раздел 12), групповых чатов в этом ТЗ нет.
- **Писать можно тому, с кем есть учебная связь.** Не «любой любому»: право отправки выводится из курсов
  (раздел 3) и проверяется при каждой отправке, а не один раз при создании диалога.
- **Переписка закрыта.** Текст сообщений не читают администраторы, `ashyq_ro`, ИИ, аналитика и журналы.
  Единственное исключение - сообщение, на которое пожаловался участник диалога (раздел 6).
- **Событие - подсказка перечитать.** Свежесть держится на `/me/events` и Query, без опросов и таймеров; ничего не
  опирается на повтор событий из Redis, которого после фазы 4 REWRITE не будет.
- **Впрок под v3.** Никаких новых строк прав v2, общей таблицы идемпотентности и Redis-лимитов: всё выражено
  через курс, команду курса, зачисление и Postgres (REWRITE 4.3-4.5, 6.3).
- **Не ломать существующее.** Обсуждения курса остаются местом для вопросов «всем»; колокол уведомлений не
  дублирует диалоги.

## 1. Термины и название

| Термин | Значение |
| --- | --- |
| Диалог (`conversation`) | переписка двух пользователей; у пары ровно один диалог |
| Сообщение (`message`) | одна реплика в диалоге |
| Собеседник (`peer`) | второй участник диалога |
| Связь | основание, по которому один может писать другому (раздел 3) |

Конфликт названий: сейчас «Диалоги» - это список тредов вкладки «Вопросы» ИИ-панели (`ai_threads` и ещё пять
ключей в `messages/*/ai.json`), а глоссарий требует пары «диалог - сұхбат - conversation». Новый раздел забирает
слово «Диалоги»; треды ИИ переименовываются в «Беседы» («Новая беседа», «Удалить беседу…»; kk «Әңгімелер», en
«Chats») в том же изменении, строка глоссария остаётся за личными сообщениями (решение 14.1).

## 2. Объём

Этап 1 (это ТЗ описывает его полностью):

- диалоги один на один, текст с разметкой Markdown;
- список диалогов, непрочитанное, значок в верхней панели;
- начало диалога из курса, списка учащихся, проверки работы, профиля и аналитики;
- удаление своего сообщения, жалоба на чужое, разбор жалоб и запрет отправки у администратора;
- живое обновление через `/me/events`.

Не входит никогда без отдельного решения: групповые чаты и чат курса (есть обсуждения), статус «в сети»,
«печатает…», отметка «прочитано» у собеседника (14.4), реакции, пересылка, закрепление, голос и видео, поиск по
тексту сообщений, редактирование отправленного, сквозное шифрование, push-уведомления.

## 3. Кто кому может писать

Функция `can_message(отправитель, получатель)` в домене - единственное место решения. Отправка разрешена, когда
выполнено всё:

1. Оба - действующие учётные записи (`disabled_at IS NULL`, `deleted_at IS NULL`), это разные люди.
2. У отправителя нет запрета отправки (`message_bans`, раздел 6).
3. Есть хотя бы одна связь:

| Связь | Условие |
| --- | --- |
| Курс: учащийся и команда | есть не удалённый и не архивный курс, где один - активный член команды (`course_staff.status = 'active'`) не в роли наблюдателя (`authorship <> 'reporter'`), а другой зачислен (`enrolments`) и не входит в команду |
| Курс: команда между собой | оба - активные члены команды одного не удалённого и не архивного курса |
| Администратор | отправитель имеет возможность `admin.users` - пишет любому |
| Ответ администратору | в диалоге уже есть сообщение собеседника, у которого `admin.users`; бессрочно, пока у собеседника эта возможность |

- Учащийся учащемуся писать не может (14.2). Наблюдатель курса (`reporter`) переписывается с командой, но не с
  учащимися: он не преподаёт. Группы (`usergroups`, `usergroup_courses`) связью не являются: связь даёт только
  зачисление (на 2026-11 привязок групп к курсам в данных нет).
- Связь проверяется на момент отправки. Отчисление, выход из команды, архивация или удаление курса закрывают
  отправку, но не чтение: диалог остаётся у обоих, поле ввода заменяет строка причины.
- Правило написано в терминах v3 (`course_staff`, `enrolments`, три глобальные роли). В v2 оно читает те же
  таблицы; новых строк `resource:action:scope` и новой `Capability` не появляется.
- Чужой диалог и чужое сообщение - это 404, а не 403: существование переписки не раскрывается.

Ответ сервера несёт решение, клиент его не выводит сам: `allowed_actions` диалога (`send`) и `deny_reason`
(`no_relation` | `banned` | `peer_unavailable`), у сообщения - `delete` (своё, не удалено) и `report` (чужое, не
удалено).

## 4. Данные

Все таблицы - в схеме `core`, `uuid` с `uuidv7()`, `timestamptz`, комментарий на каждой таблице; имена сверяются
с `naming_rules.rs` (автор - `user_id`, не `sender_id`).

```sql
conversations (id uuid pk, kind text check (kind = 'direct'),
  last_message_id uuid null -> messages(id), created_at)
  -- диалог создаётся только вместе с первым сообщением; last_message_id - указатель для сортировки списка

conversation_members (conversation_id -> conversations on delete cascade, user_id -> users,
  peer_id -> users, last_read_message_id uuid null, created_at,
  pk (conversation_id, user_id), unique (user_id, peer_id))
  -- две строки на диалог; unique (user_id, peer_id) гарантирует один диалог на пару и даёт поиск «мой диалог с X»
  индексы: (peer_id)

messages (id uuid pk, conversation_id -> conversations on delete cascade, user_id -> users,
  body text check (char_length(body) <= 4000), status text check (status in ('active','deleted')),
  deleted_at null, client_key uuid, course_id null -> courses on delete set null,
  activity_id null -> activities on delete set null, created_at,
  unique (user_id, client_key))
  индексы: (conversation_id, id desc), (user_id, id desc), (course_id), (activity_id)

message_reports (id uuid pk, message_id -> messages on delete cascade, reported_by -> users,
  reason text check (char_length(reason) between 1 and 1000), body_snapshot text,
  status text check (status in ('open','resolved')), resolved_by null -> users, resolved_at null,
  resolution text null, created_at, unique (message_id, reported_by))
  индексы: (status, id desc), (reported_by), (resolved_by)

message_bans (user_id pk -> users, banned_by -> users, reason text, created_at)
  индексы: (banned_by)
```

- Счётчиков нет: число непрочитанных считается при чтении (`id > last_read_message_id AND user_id <> я AND
  status = 'active'`) по индексу `(conversation_id, id desc)`, как счётчики обсуждений с 2026-11.
- `client_key` - ключ идемпотентности отправки (REWRITE 4.5): повтор с тем же ключом возвращает сохранённое
  сообщение, общая таблица `ops.idempotency_keys` не используется.
- `course_id` / `activity_id` - необязательный контекст («по курсу…», «по заданию…»), задаётся там, откуда начали
  писать; сервер проверяет, что активность принадлежит курсу и курс виден отправителю.
- Удалённое сообщение - надгробие: `status = 'deleted'`, `body = ''`, строка остаётся, чтобы не рвать порядок и
  указатели прочтения.
- Гонка двух первых сообщений навстречу: нарушение `unique (user_id, peer_id)` ловится, транзакция повторяется с
  уже существующим диалогом.
- Обязательные правки рядом с миграцией: `apply_role_grants` скрывает от `ashyq_ro` `messages.body`,
  `message_reports.reason`, `body_snapshot`, `resolution`, `message_bans.reason` (и `infra/tests/db-roles.sh`);
  `cascade_audit.rs` (каскады с `conversations` и `messages`), `fk_index_audit.rs`, `erasure.rs` (раздел 7),
  `just schema-docs`, `docs/agents/DATA.md`.
- Бюджет REWRITE (не более 35 таблиц): +5 таблиц. Это цена функции, владелец принимает её решением 14.6.

## 5. API

Тег `conversations`. Ошибки - problem+json, пагинация - `{items, next_cursor}`, предел страницы 50 (по умолчанию
30 сообщений, 20 диалогов).

| Операция | Что делает |
| --- | --- |
| `GET /me/conversations?cursor&limit&unread_only` | мои диалоги, новые сверху (по `last_message_id`): `id`, `peer {id, username, display_name, avatar_key, available}`, `last_message {id, user_id, excerpt, created_at_unix, deleted}`, `unread_count`, `allowed_actions`, `deny_reason` |
| `GET /me/conversations/unread-count` | `{conversations}` - число диалогов с непрочитанным |
| `GET /me/conversations/peers/{user_id}` | диалог с человеком до первого сообщения: `conversation_id` (или null), `peer`, `allowed_actions`, `deny_reason` |
| `GET /me/message-recipients?q&course_id&cursor&limit` | кому я могу написать: люди со связью (раздел 3), с названием общего курса и ролью в нём; `q` - `search_fold` по имени и логину |
| `GET /conversations/{conversation_id}/messages?cursor&limit` | сообщения, новые сверху; первая страница несёт `peer`, `allowed_actions`, `deny_reason`, `last_read_message_id` |
| `POST /messages` | `{to_user_id, body, client_key, course_id?, activity_id?}` -> сообщение с `conversation_id`; создаёт диалог, если его нет |
| `PUT /conversations/{conversation_id}/read` | `{last_read_message_id}`; указатель только растёт |
| `DELETE /messages/{message_id}` | автор удаляет своё сообщение (надгробие) |
| `POST /messages/{message_id}/report` | `{reason}`; участник диалога, чужое сообщение, один раз |
| `GET /admin/message-reports?status&cursor&limit` | жалобы (`admin.users`) |
| `GET /admin/message-reports/{report_id}` | жалоба, снимок текста, до 5 сообщений до и после |
| `POST /admin/message-reports/{report_id}/resolve` | `{resolution, ban}`; `ban: true` ставит запрет отправки автору |
| `DELETE /admin/message-bans/{user_id}` | снять запрет |

Правила:

- `body`: после обрезки пробелов 1-4000 символов, проверка URL как в `rich_text::validate` не нужна - это
  Markdown, ссылки обезвреживает рендер клиента; управляющие символы (кроме перевода строки и табуляции)
  отбрасываются. `excerpt` - первые 140 символов текста без разметки.
- Отправка - одна транзакция: проверка `can_message`, лимиты, диалог и участники (если нужны), сообщение,
  `last_message_id`, указатель прочтения автора; событие - после фиксации (а после REWRITE 4.4 - `NOTIFY` внутри
  транзакции).
- Лимиты считаются в Postgres по `messages (user_id, id desc)`, без Redis: 20 сообщений в минуту и 300 в сутки на
  отправителя; новых диалогов - 20 в сутки (у команды курса и администратора - 200). Превышение - 429
  `rate-limited` с `details.limit` и `retry_after`.
- Новые коды в реестре `ErrorCode`: `message-recipient-not-allowed` (403, `details.reason` = `deny_reason`),
  `messages-banned` (403). Остальное - существующие `not-found`, `validation`, `rate-limited`, `conflict`.
- `If-Match` и `version` не используются: сообщение не редактируется.
- События `UserEvent` (оба - обоим участникам, чтобы обновлялись и другие вкладки автора):
  `message.created {conversation_id, message_id, user_id}` и `conversation.updated {conversation_id}` (удаление,
  прочтение). Четыре шага добавления вида - `events/user.rs`, `dto/me.rs`, помощник рассылки, комментарий
  `sse.rs`.
- Каждая операция получает строку в `permission_matrix.rs` (семь вызывающих) и проходит `rbac_sweep`.
- Бюджет REWRITE (не более 120 операций): +13.

## 6. Жалобы и запрет отправки

- «Пожаловаться» доступно участнику на чужое не удалённое сообщение; причина обязательна. В жалобу копируется
  текст сообщения (`body_snapshot`), поэтому последующее удаление автором жалобу не обесценивает.
- Администратор (`admin.users`) видит: кто, на кого, причину, снимок текста и до 5 соседних сообщений с каждой
  стороны в их текущем виде. Других путей к чужой переписке у администратора нет - ни списка диалогов
  пользователя, ни поиска.
- Решение: текст решения и, по выбору, запрет отправки автору. Запрет не трогает чтение и уже отправленное;
  отправка отвечает 403 `messages-banned`, в диалогах - строка «Вам запрещено отправлять сообщения».
- Чтение жалобы с контекстом, решение, запрет и снятие запрета пишутся в журнал аудита (сейчас
  `ops.auth_audit_log`, в v3 - `audit_log`) без текста сообщений.
- Заявитель получает уведомление в колокол о решении (`message_report_resolved`, новая строка
  `notification_kinds`); автор сообщения о жалобе не уведомляется.
- Автоматической фильтрации текста нет.

## 7. Приватность, хранение, стирание

- Текст сообщений не попадает: в журналы и трассировки (только идентификаторы), в аналитику, в промпты, поиск
  по смыслу и память ИИ, в `ashyq_ro`. Отдельного события в `analytics_events` нет: счёт диалогов и ответов
  (раздел 13) читается из самих `messages` и `conversation_members` без текста.
- Копия продакшена на dev-хосте теперь содержит переписку: правило «данные остаются на этом хосте, снимки - под
  `tmp/`» распространяется на неё без изменений; e2e и снимки экранов работают только с диалогами тестовых
  учётных записей.
- Срок хранения: диалог без новых сообщений 1095 дней удаляется целиком заданием `maintenance:retention`
  (`RetentionConfig.messages_days`, решение 14.5). Решённые жалобы живут вместе с сообщением.
- Стирание учётной записи (`erase_personal_data`): сообщения стёртого становятся надгробиями, его жалобы и запрет
  удаляются, строки участника остаются - собеседник видит диалог с «Удалённый пользователь» и без права писать.
  Классификация в `erasure.rs`: `messages.user_id` - ERASED (тело), `conversation_members.user_id/peer_id` -
  RECORD, `message_reports.reported_by` - ERASED, `resolved_by` и `message_bans.banned_by` - ACTOR.
- Отключённая учётная запись: диалоги сохраняются, собеседник видит `peer.available = false` и не может писать.
- Выгрузки переписки пользователю нет (как и остальных данных).

## 8. Уведомления

- Свой счётчик - значок «Диалоги» в верхней панели с числом диалогов с непрочитанным. Колокол о сообщениях
  молчит: два сигнала об одном событии не нужны, а срок жизни уведомлений (90 дней) и их отказ по видам к
  переписке не подходят.
- Прочтение: диалог считается прочитанным, когда его лента открыта в видимой вкладке; клиент отправляет `read` с
  id последнего показанного сообщения.
- Почта и push на этапе 1 отсутствуют (REWRITE 2: «push/email notification feeds» - не цель). Следствие, о
  котором владелец должен знать: преподаватель увидит сообщение, только когда зайдёт на платформу. Почтовая
  сводка - этап 3 (раздел 12, решение 14.3).

## 9. Интерфейс (web-2)

Фича `src/features/conversations`, каталоги `messages/{ru,kk,en}/conversations.json`, ключи `conversations_*`.
Маршруты под `_authed`; гость кнопок «Написать» не видит.

| Где | Что |
| --- | --- |
| Верхняя панель, все пространства | новый слот `messages` в `shell-slots.ts` рядом с колоколом: иконка-ссылка на `/conversations`, значок числа как у колокола (`bg-highlight`, «99+»), подпись для экранного чтеца с числом |
| `/conversations` (`ListPage`) | список диалогов: аватар, имя, начало последнего сообщения (у своего - «Вы: …», у удалённого - «Сообщение удалено»), дата, число непрочитанных; строка - растянутая ссылка; фильтр `?unread=true`; «Показать ещё»; основная кнопка «Написать» |
| `/conversations/new?to=<user_id>&course=&activity=` | выбор получателя (поиск по `message-recipients`, группировка по курсу) или, при `to`, сразу поле ввода; уже существующий диалог перенаправляет в него; после первой отправки - переход в диалог |
| `/conversations/$conversationId` (`DetailPage`) | заголовок - имя собеседника (ссылка на профиль) и общий курс; лента; поле ввода внизу |
| `/admin/message-reports` (`ListPage`) и `?report=<id>` | открытые и решённые жалобы; карточка жалобы с контекстом, «Решить» (`FormDialog`: решение, флажок запрета) |

Точки входа «Написать» (ссылка на `/conversations/new` с `to` и контекстом; показывается, когда
`peers/{user_id}` или строка списка разрешает `send`):

- страница курса - у каждого преподавателя в блоке команды;
- список учащихся курса в рабочем месте преподавателя - действие строки (без запроса `peers` на каждую строку: у
  команды курса связь есть всегда, запрет или удалённая учётная запись показывают причину на следующей странице);
- страница проверки работы - «Написать учащемуся» с контекстом активности;
- публичный профиль `/users/$username` - для вошедшего со связью;
- аналитика - рекомендация «Написать личное сообщение» ведёт в диалог с учащимся с контекстом курса (запись
  вмешательства `message_sent` остаётся отдельным действием преподавателя до этапа 2).

Лента:

- Порядок - старые сверху, новые снизу; открытие ставит вид на первое непрочитанное (перед ним разделитель «Новые
  сообщения») или на конец; «Показать более ранние» сверху сохраняет положение прокрутки.
- Сообщение: аватар, имя, время; подряд идущие сообщения одного автора в пределах 5 минут - без повтора шапки.
  Разделители дней. Без «пузырей» и карточек: строки на странице, своё сообщение отмечено `border-s-2`, как ход
  пользователя в ленте ИИ (DESIGN: секции - не коробки, цвет - не единственный сигнал).
- Текст - `MarkdownView` (GFM, формулы, код; сырой HTML не исполняется, ссылки через `safeUrl`). Контекст
  сообщения - строка-ссылка «По курсу …» / «По заданию …» над текстом.
- Удалённое - «Сообщение удалено» приглушённым текстом. Меню сообщения: «Удалить» (`ConfirmDialog` с началом
  текста) у своего, «Пожаловаться» (`FormDialog` с причиной) у чужого.
- Лента - `role="log"` с `aria-live="polite"`: пришедшее сообщение объявляется, история при подгрузке - нет.

Поле ввода:

- `Textarea`, растёт до 6 строк; «Отправить» - единственная основная кнопка, выключена при пустом тексте и на
  время запроса; счётчик появляется за 200 символов до предела.
- Enter отправляет, Shift+Enter - перенос; на устройствах без точного указателя Enter - перенос, отправка
  кнопкой.
- Оптимистичной вставки нет (в web-2 её нет нигде): сообщение появляется из ответа сервера и кладётся в кэш.
  Отказ - текст остаётся в поле, под ним ошибка по коду и «Повторить» с тем же `client_key`.
- Нет права писать - вместо поля одна строка причины по `deny_reason` (нет общего курса; собеседник недоступен;
  вам запрещено отправлять сообщения).
- Черновик живёт, пока открыта вкладка; между перезагрузками не хранится.

Живое обновление:

- Строки `message.created` и `conversation.updated` в `event-invalidations.ts` перечитывают счётчик панели, список,
  открытую ленту и ответы `peers/{user_id}`; отдельного `live.ts` нет - данных события на правку кэша на месте не
  хватает (в нём только идентификаторы). Скрытая вкладка поток не держит - при возвращении запросы перечитываются,
  как у уведомлений.
- Тост о новом сообщении не показывается (DESIGN: тосты - только из `onSuccess` своей мутации); сигнал - значок.

Общий код: слот `messages` верхней панели, `formatTime` и `platformDay` в `shared/i18n/format.ts`, строка
«Жалобы» раздела администрирования в `shared/auth/access.ts` (право `admin.users`, как у сервера); 390 px без
горизонтальной прокрутки проверяет `conversations.spec.ts`. Двухпанельного шаблона (список +
лента) в DESIGN нет и на этапе 1 он не вводится: список и лента - две страницы, что и есть раскладка телефона.

Тексты - на ru, kk и en, обращение на «вы» / «сіз»; kk и en для «диалог» - «сұхбат» / «conversation» (глоссарий).

## 10. Проверка качества

- Сервер: модульные тесты `can_message` по каждой строке таблицы раздела 3 и каждому отказу; HTTP-тесты
  (`conversations_*_flow.rs`): первая отправка создаёт диалог, встречная гонка даёт один диалог, повтор
  `client_key` не дублирует, чужой диалог - 404, отчисление закрывает отправку и оставляет чтение, архив курса,
  лимиты, надгробие, жалоба со снимком, запрет и его снятие, стирание учётной записи, событие обоим
  участникам (`sse_flow`), удаление по сроку; строки `permission_matrix.rs`, `cascade_audit.rs`, `erasure.rs`,
  проверка грантов `ashyq_ro`.
- web-2: модели (группировка ленты, разделители дней, цель контекстной ссылки, причины отказа) - unit; список,
  лента, поле ввода, жалоба - browser-тесты с подменой `fetch`; e2e `conversations.spec.ts`: учащийся пишет
  преподавателю, у преподавателя значок появляется из события без перезагрузки, ответ, удаление, отказ без
  связи, 390 px; axe и темы - общими воротами.
- Живая проверка на слоте 1 двумя тестовыми учётными записями (`just login-as`), снимки `just shoot` в `tmp/`.

## 11. Критерии приёмки этапа 1

1. Учащийся со страницы курса пишет преподавателю; преподаватель, открытый в другой вкладке, видит значок без
   перезагрузки, отвечает, учащийся видит ответ.
2. Учащийся не может написать преподавателю чужого курса и другому учащемуся ни через интерфейс, ни прямым
   запросом (403 `message-recipient-not-allowed`); чужой диалог отвечает 404.
3. После отчисления диалог читается, отправка закрыта с причиной; после повторного зачисления открыта снова.
4. Повтор отправки при обрыве сети не создаёт второго сообщения.
5. Жалоба доходит до администратора со снимком текста; запрет отправки действует сразу и снимается.
6. `ashyq_ro` не читает текст сообщений; в журналах сервера текста нет.
7. Стирание учётной записи оставляет собеседнику диалог с надгробиями.
8. Все экраны проходят на ru, kk, en, в светлой и тёмной теме, на 390 px, с клавиатуры.
9. `just ci` зелёный; контракт (`just contract`) и `docs/agents/SCHEMA.md` обновлены.

## 12. Этапы

| Этап | Состав | Зависимости |
| --- | --- | --- |
| 1 | всё выше | решения 14.1, 14.2, 14.6 |
| 2 | вложения: назначение загрузки `message-attachment` (приватное хранилище, до 5 файлов по 20 МБ, выдача только участникам диалога, `message_uploads` + строка в `upload_referenced`); сообщение нескольким учащимся из списка курса (отдельное сообщение в каждый диалог, до 50 адресатов); запись вмешательства `message_sent` той же транзакцией, что и отправка из аналитики | после переноса медиа на диск (REWRITE фаза 4.2), чтобы не строить на RustFS |
| 3 | почтовая сводка: задание раз в сутки, одно письмо «у вас N непрочитанных диалогов» без текста сообщений, отказ в настройках уведомлений | решение 14.3, рабочая почта (REWRITE фаза 0) |
| Вне плана | переписка между учащимися с блокировкой собеседника; чат группы или курса; двухпанельный шаблон | отдельные ТЗ |

Порядок работ этапа 1: миграция и запросы -> домен (`community/messages.rs`: `can_message`, отправка, чтение,
жалобы) -> маршруты, матрица прав, `just contract` -> фича web-2 и слот панели -> точки входа -> жалобы в
администрировании -> переименование тредов ИИ -> e2e. Сервер и web-2 - разные наборы файлов, их могут вести два
исполнителя после фиксации контракта.

## 13. Риски

| Риск | Что делаем |
| --- | --- |
| Функцией не пользуются (как обсуждениями) | этап 1 минимален; через 60 дней после выпуска - число диалогов и отвечённых сообщений, по ним решаются этапы 2-3 |
| Преподаватель не видит сообщение без почты | значок во всех пространствах; этап 3; интерфейс нигде не обещает учащемуся быстрый ответ |
| Преподавателя заваливают сообщениями | лимит новых диалогов, запрет отправки, отсутствие «прочитано» снимает давление |
| Травля и споры | жалоба со снимком, запрет отправки, аудит действий администратора |
| Утечка переписки | гранты `ashyq_ro`, запрет текста в журналах и ИИ, тесты на оба |
| Заморозка REWRITE | решение 14.6; всё спроектировано под целевую схему v3, переделывать при фазах 4-5 не придётся |

## 14. Решения владельца

Приняты 2026-11-10, все - вариант по умолчанию.

1. **Название.** Раздел называется «Диалоги», треды ИИ становятся «Беседами» (kk «Әңгімелер», en «Chats»).
2. **Учащийся учащемуся.** Нельзя; блокировки собеседника на этапе 1 нет.
3. **Почта.** Этапом 3, после данных об использовании; это отменяет строку «не цель» REWRITE 2 для одного письма
   в сутки.
4. **Отметка «прочитано» у собеседника.** Не показывается.
5. **Срок хранения.** 3 года без новых сообщений.
6. **Когда делать.** Исключение из заморозки REWRITE (фаза 0, раздел 13) для этапа 1: +5 таблиц и +13 операций.
7. **Администратор как адресат.** Учащийся не может первым написать администратору, только ответить; право ответа
   бессрочное.
8. **Наблюдатель курса.** `reporter` переписывается с командой курса, но не с учащимися.
